# Sionna RT handoff — ARA rural COTS RAN digital twin (Ames, Iowa)

Everything needed to run ray-tracing simulations against the Arathon Challenge-3
measurement campaign. The Blender/Blosm scene-building stage is **already done** — you do
not need Blender, OpenStreetMap, or a DEM. Start from the Mitsuba scene in `mitsuba/`.

Generated by `make_bundle.sh`; the same files live in `scene/` in the repository.

```
mitsuba/ames.xml                       the scene: load this
mitsuba/meshes/Terrain.ply             457k-vert terrain, 30 m posts
mitsuba/meshes/ames_osm_buildings.ply  10,079 buildings
georef.json                            projection constants — READ THESE, don't re-derive
calibrate.py                           score predictions against measured RSRP
predict_surface.py                     predict over a grid + at every measured point
build_terrain_3dep.py                  optional 10 m terrain rebuild (see "Don't bother")
make_figure.py                         3-panel measured / predicted / validation figure
pred_30m_h30.npz                       precomputed surface (30 m terrain, 30 m antenna)
coverage_validation.png                that figure, already rendered
dem_3dep.tif                           10 m DEM, used only for the figure's hillshade
data/COTS.csv                          7,144 UE measurements
data/Base_Station_Information.yaml     4 sites, 3 cell IDs each
```

## 1. Setup

```bash
pip install sionna-rt          # 2.0.1; pins mitsuba 3.8.0, drjit 1.3.1
```

### On a CUDA GPU (recommended)

Nothing else to configure. Sionna tries the `cuda_ad_mono_polarized` Mitsuba variant first
and only falls back to LLVM if no GPU is available, so **`DRJIT_LIBLLVM_PATH` is not
needed.** Confirm which backend you actually got — a silent CPU fallback is the usual
reason a "GPU run" is slow:

```python
import mitsuba as mi; print(mi.variant())   # want: cuda_ad_mono_polarized
```

**Raise the chunk size.** `predict_surface.py` batches receivers because `PathSolver`
degrades badly with receiver count, and the default of 800 is tuned for a CPU backend. On a
GPU the limit is VRAM, not time — start an order of magnitude higher and back off if you
hit an allocation error:

```bash
RT_CHUNK=8000 python predict_surface.py mitsuba/ames.xml 30 pred.npz 100
```

A finer grid also becomes affordable: the last argument is grid spacing in metres, and 100 m
or 50 m is where the coverage map starts looking like a map rather than a mosaic. Grid
points scale quadratically — 200 m gives 6.6k receivers, 100 m gives 26k, 50 m gives 105k.

The whole 2x2 terrain/diffraction sweep in section 4 took ~50 min on CPU; it is worth
re-running on GPU with more receivers, since several conclusions there rest on only 800
sampled points.

### On CPU (macOS / no GPU)

**Sionna RT will not import without `DRJIT_LIBLLVM_PATH`.** Any libLLVM from a conda env,
Homebrew `llvm`, or the Xcode toolchain works:

```bash
export DRJIT_LIBLLVM_PATH=/path/to/libLLVM.dylib   # e.g. .../radioconda/lib/libLLVM-19.dylib
```

The failure looks like:

```
ImportError: jit_init_thread_state(): the LLVM backend is inactive because the LLVM
shared library ("libLLVM.dylib") could not be found!
```

Verify:

```bash
python -c "
from sionna.rt import load_scene
s = load_scene('mitsuba/ames.xml', merge_shapes=False)
print({n: o.radio_material.name for n, o in s.objects.items()})"
# -> {'ames_osm_buildings': 'itu_concrete', 'Terrain': 'itu_medium_dry_ground'}
```

Materials resolve through Sionna's naming convention: a BSDF whose id is `mat-itu_<type>`
becomes the corresponding built-in `ITURadioMaterial`. Don't rename them.

## 2. Coordinates — read `georef.json`, never re-derive

Scene units are metres. Mitsuba XY equals Blender XY equals the projected frame below
(the scene was exported with an identity axis conversion, so nothing is rotated).

The projection is a **spherical transverse Mercator**, `radius = 6378137`, `k = 1`, centred
on `origin_lat = 41.98499870300293`, `origin_lon = -93.7599983215332`. Round-trip error is
1e-10 m. `predict_surface.py` has a working `fromGeo()` — copy it rather than rewriting.

```python
def fromGeo(lat, lon):                      # WGS84 -> scene XY, metres
    lat = np.radians(lat); lon = np.radians(lon - LON0)
    B = np.sin(lon) * np.cos(lat)
    return (0.5 * K * R * np.log((1 + B) / (1 - B)),
            K * R * (np.arctan(np.tan(lat) / np.cos(lon)) - lat0r))
```

Two traps:

- **Terrain z is 262 m below true elevation** (Blosm's `height_offset`). Irrelevant to RF,
  since only relative heights matter, but it will bite any comparison against a real DEM.
- **Do not use a fixed `cos(lat)` approximation.** Across this 22 km box that costs ~8 m at
  the corners, which is the same order as the DEM post spacing.

To place a receiver on the ground, ray-cast down — `predict_surface.py:ground_z()`. The
base stations are pre-resolved in `georef.json`:

|---|---|---|---|---|

## 3. Radio configuration recovered from the data

- **Carrier 3.4608 GHz** (NR-ARFCN 630720). Single-valued across the whole dataset, so
  `band` and `arfcn` are useless as ML features.
- **Agronomy Farm is a standard three-sector site.** The cell-ID suffix encodes the sector,
  and binning served points by bearing gives each a clean contiguous arc:

  | cellid | compass azimuth |
  |---|---|
  | `00019C00B` | 0 deg |
  | `00019C015` | 115 deg |
  | `00019C01F` | 240 deg |

  Sionna orientation is `[yaw, pitch, roll]` in radians with yaw measured from +x
  (East), so `yaw = radians(90 - azimuth_compass)`.
- **Antenna height, tilt and EIRP are not in the dataset.** Height is currently swept;
  EIRP + antenna gain is absorbed into a single fitted `offset` constant (~25 dB).

## 4. What is already known — don't redo these

Best configuration: **30 m terrain, `diffraction=False`, `max_depth=3`, LOS + specular.**
Against 800 sampled Agronomy rows that gives **corr 0.79, RMSE 9.0 dB**.

**Don't bother with a finer DEM.** USGS 3DEP 1/3 arc-second (7.7 x 10.3 m posts, 8.2M
triangles) scores 9.14 dB against the 30 m mesh's 8.99 dB — no improvement for 18x the
geometry. `build_terrain_3dep.py` is included only so the result can be reproduced; the
DEM it needs is one request:

```bash
curl -o dem_3dep.tif "https://elevation.nationalmap.gov/arcgis/rest/services/3DEPElevation/ImageServer/exportImage?bbox=-93.8950,41.9200,-93.6250,42.0500&bboxSR=4326&size=2916,1404&imageSR=4326&format=tiff&pixelType=F32&f=image"
```

**Don't just switch diffraction on.** `diffraction=True, edge_diffraction=True` makes the
fit *worse* on both meshes (11.7 dB on 30 m, 10.6 dB on 10 m). A tessellated DEM presents
every triangle boundary as a candidate diffracting edge with an unphysically large dihedral
angle. It degrades less on the finer mesh, which is the signature of a tessellation
artifact rather than real physics. If you want diffraction, restrict it to the buildings.

**Chunk your receivers.** `PathSolver` scales far worse than linearly: 800 receivers solve
in ~15 s, but a single 15,742-receiver call ran 30 minutes without finishing. Chunked, the
same work is linear at ~31 s per 1,500. Tune with `RT_CHUNK` (see section 1).

## 4b. Reproducing the figure

```bash
python predict_surface.py mitsuba/ames.xml 30 pred.npz 200   # ~4 min, 10.4k receivers
python make_figure.py pred.npz out.png
```

Held-out result with the shipped `pred_30m_h30.npz`: **n = 1,763, RMSE 8.6 dB, r = 0.82,
bias +1.7 dB**, where the calibration constant is fitted only on the complementary
checkerboard of 2 km blocks. 57% of grid cells get a modelled path; the other 43% are grey
in panel (b) and are a known limitation, not an absence of coverage.

## 5. The open problems — this is where the work is

1. **Antenna height is not identifiable.** The sweep is flat from 15 to 60 m in every
   configuration tried. Note the RMSE is *not* comparable across heights: a taller antenna
   links more receivers and the extra ones are marginal far-out points that predict badly,
   so low heights score better partly by being graded on an easier subset. **Compare on a
   common linked subset before concluding anything about height.**
2. **6-27% of points where the UE genuinely reported RSRP get no traced path at all.**
3. **Where the residual is not:** terrain resolution (ruled out), diffraction (ruled out).
   Still open: vegetation — `forests` and `vegetation` were excluded from the scene
   entirely, and Iowa shelterbelts attenuate at 3.46 GHz even in a bare-field March; the
   `itu_concrete` / `itu_medium_dry_ground` material choices; and the `tr38901` pattern
   versus the real sector antenna.
4. **Research Park is a free negative control.** It serves 0 of 7,144 rows. Any model that
   predicts usable coverage from it is wrong regardless of how well it fits Agronomy.

## 6. Data traps in `COTS.csv`

- `sinr` and `rsrq` load as **object dtype** — 11 rows contain a literal `'-'`. Always
  `pd.to_numeric(..., errors='coerce')`.
- `cellid = FFFFFFFFF` with `arfcn = -1` is a **no-service state**, not a measurement, even
  though those rows carry RSRP, SINR and sometimes throughput.
- **42% of rows have no serving cell.** They are the strongest signal in the dataset and
  they live in exactly the rows a naive `dropna()` discards.
- Consecutive samples are ~22 m apart, so **a random train/test split leaks badly.** The
  challenge brief requires geographically separated test segments — split by spatial block
  or by run. `predict_surface.py` uses a 2 km checkerboard.
- Missing uplink/downlink is **not missing-at-random** — it is missing exactly where
  service failed, which biases any service surface optimistic in precisely the places
  Challenge 3 cares about.
- **Uplink is the binding constraint, not downlink.** Downlink saturates ~230 Mbps for any
  SINR > 0; uplink tracks RSRP hard and spans 8-63 Mbps. Define "underserved" on uplink.
